# Evaluation Strategy

Current evaluation design for committed `urban-gala-v2`, verified 2026-06-09.
Updated with M004 evaluation hardening (96-question benchmark, graded relevance,
RAGAS faithfulness, cross-encoder ablation, CI-gated reports).

## Retrieval benchmark

`BackEnd/llm-service/data/benchmark.jsonl` contains **96 curated questions** across
five categories. Each case records expected venue identifiers, graded relevance
labels, and any relevant filter or conversational context.

### Relevance grades

In addition to binary expected-venue membership, each question assigns **graded
relevance** (3=perfect, 2=good, 1=partial) to expected venues:

| Grade | Meaning | Example |
|-------|---------|---------|
| 3 | Perfect match — venue directly matches query intent and tags | "Italian restaurants" → Italian-tagged restaurant |
| 2 | Good match — venue fits the query well | "cozy bars" → bar with intimate/elegant tags |
| 1 | Partial match — venue is acceptable but less ideal | "fine dining" → moderate restaurant with some fine dining tags |

Graded NDCG@5 uses these grades instead of binary relevance, producing a
rank-sensitive metric that rewards ranking perfect matches above partial matches.

### Category distribution

| Category | Count | Purpose |
|----------|-------|---------|
| retrieval | 22 | Open-ended semantic/tag-based venue search |
| filtered | 20 | Zone, price, and combined filter queries |
| conversational | 18 | Context-dependent follow-up questions |
| adversarial | 18 | Hallucination-probing queries (attributes not in corpus) |
| abstention | 18 | Out-of-domain/geography queries (should return empty) |

`scripts/run_eval.py` can:

- Run the configured retrieval pipeline.
- Compare dense-only retrieval with the improved configuration.
- Report per-question, per-category, and aggregate metrics.
- Emit JSON reports.
- Run metrics-only mode without threshold enforcement.

## Metrics

| Metric | Meaning |
|--------|---------|
| Recall@5 | Fraction of expected relevant venues found in the first five results |
| Graded NDCG@5 | Rank-sensitive gain using relevance grades (3/2/1) instead of binary |
| Precision@5 | Fraction of the first five results that are expected relevant venues |
| MRR | Reciprocal rank of the first relevant result |
| Hit Rate | Fraction of queries with at least one relevant result |

The harness also tests citation parsing, abstention-related behavior, filters,
query expansion, multi-turn context, BM25, RRF, cross-encoder fallback, and
index integrity through pytest.

## Recorded comparison (96-question benchmark)

| Metric | Dense baseline | Improved configuration | Delta |
|--------|---------------:|-----------------------:|------:|
| Recall@5 | 0.2495 | 0.2874 | +0.0379 |
| Graded NDCG@5 | — | 0.2899 | — |
| MRR | 0.3182 | 0.3747 | +0.0566 |
| Precision@5 | 0.2121 | 0.2242 | +0.0121 |
| Hit Rate | 0.4545 | 0.4848 | +0.0303 |

*Note: The 96-question expanded benchmark is significantly harder than the original 41 —
many new questions test edge cases (combined filters, tag-based semantic retrieval, 
conversational context) that produce lower absolute scores. The CI gate threshold 
of recall@5 >= 0.25 is calibrated for the expanded set. The original 41-question 
comparison numbers are preserved above for reference; the 96-question results are 
generated by the `eval-report` CI job on every PR.*

The strongest relative result is improved ranking, especially MRR. Hybrid
retrieval also helps exact-name and rare-term queries that dense retrieval can
miss.

## Interpretation limits

- Forty-one questions are enough for regression development, not for a strong
  statistical claim about all users.
- The cases are internally curated rather than independently labeled.
- Expected IDs can reward a narrow set of acceptable answers even when other
  venues are reasonable.
- The aggregate Recall@5 of 0.2874 is still low in absolute terms.
- The improved configuration can include optional cross-encoder behavior, but
  checked-in Compose sets `CROSS_ENCODER_ENABLED=false`.
- This is not a cross-encoder-only ablation. BM25/RRF, query expansion, and
  other changes are also present, so no metric delta can be attributed to
  re-ranking alone.
- Retrieval metrics do not measure the factuality, usefulness, style, latency,
  or cost of the final generated answer.
- The Hugging Face model is external and may change behavior independently of
  repository code unless its exact model/version is controlled.

Use the results as evidence that v2 introduced a reproducible measurement loop
and improved this benchmark. Do not present them as proof of production-grade
RAG quality.

## Busyness evaluation

The busyness service test suite verifies:

- Model artifact integrity and loading behavior.
- Prediction normalization and response shape.
- Twelve-hour forecast generation.
- Weather fallback.
- CORS and route behavior.
- Bounded caching.

The repository does not publish a current holdout-set accuracy table for the
served Keras models. Historical model explanations and research are not a
substitute for a reproducible training/evaluation report.

For interviews, state that v2 hardened serving reliability and artifact
reproducibility; do not invent model accuracy, calibration, or live-ground-
truth results.

## RAGAS evaluation (answer-level groundedness)

Generation-quality evaluation measures whether LLM answers are factually grounded
in retrieved context rather than hallucinated.

**What RAGAS measures:**

| Metric | Meaning | Scale |
|--------|---------|-------|
| Faithfulness | Is every claim in the answer supported by the retrieved context? | 0–1 |
| Answer Relevancy | Does the answer actually address the user's question? | 0–1 |
| Context Precision | Are the relevant documents ranked near the top? | 0–1 |

**How it works:**

1. The benchmark question is run through the full RAG pipeline (retrieve → generate).
2. The generated answer, query, and retrieved contexts are sent to an LLM judge
   (`prompts/judge-v1.yaml`) via the Hugging Face chat API.
3. The judge returns 1–5 scores for each dimension, divided by 5 for the 0–1 scale.

**Running RAGAS:**

```bash
# Full RAGAS with real HF judge (requires HF_TOKEN)
python3 scripts/eval_ragas.py --report reports/ragas.json

# Mock mode for CI smoke testing (no API calls)
python3 scripts/eval_ragas.py --limit 10 --mock-judge --no-delay --metrics-only

# Via run_eval.py (combined retrieval + RAGAS)
python3 scripts/run_eval.py --ragas --ragas-delay 1.0 --metrics-only
```

**CI integration:** The `ragas-smoke` job in `.github/workflows/ci.yml` runs
`eval_ragas.py --limit 10 --mock-judge` on every PR to verify the RAGAS pipeline
doesn't regress. Mock mode uses synthetic judge scores and answer generation —
it validates the pipeline mechanics, not the quality scores.

**Known limitations:**

- Faithfulness scores depend on the quality of the LLM judge (Hugging Face model).
- A low faithfulness score means the answer contains unsupported claims, but a
  high score doesn't guarantee factual correctness — the context itself may be wrong.
- Mock mode (CI) produces deterministic synthetic scores; real evaluation
  requires `HF_TOKEN` in CI secrets.
- Full RAGAS eval on 96 questions takes ~4–5 minutes (HF API rate limiting).

## System quality gates

Evaluation extends beyond model metrics:

- Spring/Flask contract fixtures verify payload compatibility.
- Artifact checksums protect model/corpus reproducibility.
- Frontend tests cover AI, route, forecast, auth, plan, and cache behavior.
- Compose smoke exercises production-style service startup and proxying.
- Structured events and Prometheus metrics support future latency, failure,
  and quality monitoring.

dated executable results.
